Here's the design for 1–3. It follows the pattern already in the code: every write goes through a database function, and only the server talks to Stripe.

## 1. Saved delivery schedule
- **New `orders` columns:** `shipped_at`, `out_for_delivery_at`, `delivered_at`.
  - They're filled in when an order is placed: immediately for non-card orders, and at payment confirmation for card orders.
  - The timings match today's: shipped at +10 h, out for delivery at 9:00 local the next valid day, delivered at 11:30 local.
  - New `markets.time_zone` column: `America/Los_Angeles` for the US store, `Asia/Kolkata` for India.
- **`status` keeps its three values** (`awaiting_payment` / `placed` / `cancelled`), so existing readers don't change.
  - A new `stage` is worked out from whichever saved time has passed: `preparing` → `shipped` → `out_for_delivery` → `delivered`, or `cancelled`.
  - The order JSON includes `stage`, and admin filters use it.
- **Admin adjustments:**
  - "Mark shipped now" sets `shipped_at` to now and moves the later stages up using the same rules.
  - "Mark delivered now" sets any stages that haven't happened yet to now.

  - After delivery, the answer is Returns (not in this piece).
  - Cancelling is whole-order only.
- **The cancel function** locks the order, checks the window, sets it to cancelled, returns the stock, and records a reason (`customer` / `admin` / `sold_out`) plus the refund state:

| Payment | Refund state |
|---|---|
| Card (Stripe) | `pending`. The server then asks Stripe for the refund, using the order id so a retry can't refund twice, and saves the refund id and result. If Stripe errors, the state becomes `failed` and admin gets "Retry refund". |

| Cash on delivery | `not_charged` |
